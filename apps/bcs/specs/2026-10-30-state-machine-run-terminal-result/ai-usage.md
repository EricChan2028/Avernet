# AI 使用策略报告（Issue #2610）

- 队伍：Wake-Up Call（陈畅源、王子晔）
- 工具：Claude Code（模型 Claude Opus 5.5），运行在队员笔记本上，通过 SSH 在远程开发机上读写代码、编译和测试
- 范围：复现、设计、BCS 实现、主持人技能接入、故障注入脚本与验证、本报告

## 1. 分工

| 环节 | 人 | AI |
| --- | --- | --- |
| 选题、认领与登记 | 决定参加 #2610；确认队名和登记内容后，才由 AI 用队员账号发出 | 阅读 issue 与仓库、起草登记评论 |
| 复现 | 确认复现方式 | 搭建 singlebox，编写模拟人类玩家的脚本，注入故障并记录证据 |
| 设计 | 审阅并批准提交设计 PR | 阅读 TaskResult、队列与 StateMachine 代码，撰写设计与复现记录 |
| 实现与测试 | 审阅 PR，决定何时提交 | 编写代码与测试，运行全部相关测试与故障注入 |
| 对外操作 | 每次公开操作前明确确认（登记评论、开 PR） | 不擅自发布任何公开内容 |

AI 写了绝大部分代码和文档；对外的每一步都由队员确认后才执行。

## 2. 防止「看起来对」的做法

- **结论必须有代码出处。** 设计文档中的每个行为描述都附 `文件:行号`，由 AI 对照源码核实。
  核实中发现过错误并已改正：AI 起初以为 `uc publish-result` 能补发开票稿，读代码后发现它只在终局后可用，于是改为新增 `uc recap`。
- **先复现，再设计。** 先在真实对局里复现问题，拿到 Run、节点与事件的数据库证据，再动手设计。
- **测试覆盖验收条款，而不只是覆盖代码。** 恰好一次、回调与取消竞争、重放、可重试与结果不确定、
  会话结束或群关闭不投递、迟到产物、内容不泄露，各有对应测试；现有测试全部重跑。
- **真实环境验证。** 单元测试之外，用真实模型和 6 个 Bot 跑故障注入，统计恢复时间。
  这一步发现了单元测试发现不了的问题：模型服务限流导致主持人反应超过 60 秒，以及注入脚本自身重启 Bot 的缺陷。
  前者促成了 `uc recover` 的一次调用设计，后者已修复。

## 3. 安全与合规

- 模型 key 与 GitHub token 只保存在开发机上权限为 600 的文件里，不进入仓库、提交、日志或评论。
  仓库的 pre-push 密钥扫描对每次推送都通过。
- 访问受限网络时，代理凭据只在笔记本进程内存中使用，不写入任何文件，也不传到服务器。
- 结果消息与公开事件经测试确认不含节点产物、错误原文和玩家的词。
- 不绕过仓库的 CI 门禁与钩子。

## 4. 成本控制

- 日常开发只跑 `cargo test` 和 mock 场景；只有复现、故障注入和演示使用真实模型。
- 实测：闲置的 Bot 每 30 分钟心跳一次，每次都调用模型，一套 6 个 Bot 一天约消耗 550 万 token。
  因此不跑对局时一律停掉 Bot。
- 一轮发言加一次失败恢复约消耗 30 万 token（含缓存读取），10 次故障注入的预算按此估算。
- 编译使用 `line-tables-only` 调试信息并及时清理测试产物，避免占满与其他任务共用的磁盘。

## 5. 经验

1. 让 AI 在真实环境里跑通，比让它只写单元测试更能暴露问题。
2. 让 AI 给出可核对的出处，并且由 AI 自己去核对，能拦住大部分似是而非的结论。
3. 任何对外动作都保留人工确认这一步，哪怕代码已经全部就绪。
