# 支付宝 Agent 搜索压测方案

## 要回答的三个问题

1. 当前 Qdrant Local 在目标数据规模下，单实例能稳定处理多少检索请求？
2. 持续高流量、日志写入和后台更新会不会使吞吐下降、内存上涨或请求阻塞？
3. 完整搜索服务要承接峰值 10 万 QPM（约 1,667 QPS），需要多少实例，失去部分实例后是否仍能服务？

前两项现在就测。第三项在支付宝搜索链路接通后验证，不能用存储接口的 QPS 直接代替业务 QPS。几百个 Agent 只能说明资料数量较少，不能证明高并发下没有锁、线程池或模型配额瓶颈。

## 范围和优先级

| 优先级 | 测试位置／场景 | 怎么测 | 决定什么 |
| --- | --- | --- | --- |
| P0，现在 | 单实例向量检索、关键词检索、两者组合 | 三种 mode，真实样本和索引，逐级提高请求到达率 | 存储路径的容量和主要瓶颈 |
| P0，现在 | 持续负载 | 候选稳定档位连续 30 分钟，再跑 2 小时 | 是否有积压、内存增长和日志磁盘风险 |
| P0，现在 | 查询与资料更新并行 | 在稳定搜索负载下，由运维执行小批资料更新，随后观察更新结束后的恢复 | 现有读写锁、同步任务是否影响查询；新资料是否可被搜到 |
| P0，现在 | 日志影响 | 相同数据／负载，比较现状与显式 INFO；必要时 WARNING 仅作诊断 | 写入量与性能开销；是否需要采样、异步、缩短保留期 |
| P0，上线前 | 完整搜索接口 | 从真实入口发压，经过实际模型、筛选、排序、缓存与返回结果流程 | 端到端容量、模型配额及实例数 |
| P0，上线前 | 失效和过载 | 模型慢／不可用、一个实例退出、突发流量、缓存冷启动 | 限流、降级、摘流和恢复是否有效 |
| P1，按结果 | 独立 Qdrant Server 对照 | 只有 Local 容量／恢复性不满足或成本不合适时，用相同数据、查询、筛选、TopK 和硬件预算对比 | 是否值得迁移，避免一开始建设两套压测系统 |
| P1，按结果 | 共享缓存、向量缓存等新增能力 | 能力落地且预计节约明显时，再测命中率、回源与失效 | 缓存收益能否覆盖复杂度 |

**当前脚本只覆盖存储接口。** 完整业务链路和故障演练需使用最终业务接口，不能拿本脚本代替。重启会清除进程内样本，本脚本将中止，这不是业务可用性测试。后台更新和故障操作由运维执行，脚本不自动写数据、重启或停服务。

## 第一轮：一天内先得到存储容量结论

### 准备和检查

- 按 [接口与调用说明](retrieval-benchmark.md) 完成预发部署。固定单实例、单进程；发压机与服务端分开。记录 CPU／内存限制、两仓 SHA、Python／qdrant-client 版本、模型及维度、日志级别、并发上限。
- 使用实际预发数据，不为追求高 QPS 临时缩小索引。记录 Agent 数、片段／向量条数、平均每个 Agent 的片段数及磁盘体积。如果预发样本不能代表支付宝数据，只能给出现状基线，后续用目标资料重测。
- 准备 32—64 条业务查询词，覆盖热门、长尾、短词、长句、无匹配词。先人工检查少量命中结果；HTTP 200 不代表推荐质量合格。当前样本池最多 64 条，不用于评估大规模业务缓存命中率。
- 固定预期业务 TopK，另测一个更大的候选数，例如 10／50／100。先无筛选，再测实际使用的筛选条件，分别包含少量命中、广泛命中和无命中。不要穷举所有组合。
- 向量来自当前真实 Embedding 服务，准备后复用；搜索阶段不调用模型、不缓存结果。每次 k6 运行都会重新准备样本，向量及组合模式每轮最多 64 次模型调用，关键词模式不调用模型。

### 按顺序执行

| 步骤 | 建议负载 | 时长 | 通过后做什么 |
| --- | --- | --- | --- |
| 1. 冒烟 | 三种 mode，各 10 QPS | 各 30 秒 | 确认实例、样本、鉴权、命中及指标正常 |
| 2. 找容量拐点 | 每种 mode 依次 50、100、200、500 QPS | 每档 2 分钟 | 接近瓶颈后缩小步长；仍稳定则手动继续 800、1,200、1,667 等档位 |
| 3. 稳态确认 | 选低于容量拐点、留有余量的组合检索档位 | 30 分钟，随后 2 小时 | 记录稳定容量，而不是瞬时最高值 |
| 4. 更新／日志对照 | 同一个稳定档位 | 每组至少 15 分钟，覆盖更新前、中、后 | 判断是否需要补强锁、更新流程或日志 |

出现持续超时、大量拒绝、队列增长、内存接近限制或磁盘空间不足时停止当前轮。脚本在一轮结束后检测阈值，失败不进入下一档；它不负责实时读取服务器监控或紧急停压，需要操作人员观察监控。异常后不要反复提高流量。

### 直接运行

客户端安装 k6；设置 `BASE_URL`，OCB 预发设置 `BCSFUSE_BENCH_COOKIE`（已有登录 Cookie），独立 Bearer 模式才使用 `BCSFUSE_BENCH_TOKEN`。将 `QUERIES_FILE` 设置为真实查询 JSON 数组的**绝对路径**。凭据只从环境注入，不写入命令示例、报告或仓库。

在 Avernet 的 `apps/bcsfuse` 目录执行：

```bash
# 1. 默认三种模式，各 10 QPS、30 秒
bash scripts/run_retrieval_bench.sh

# 2. 分模式寻找容量拐点；任意一轮失败，整批停止
RATES="50 100 200 500" DURATION=2m \
  bash scripts/run_retrieval_bench.sh

# 3. 示例：只有前一步证明 200 QPS 有余量，才用它跑稳态
MODES=both RATES=200 DURATION=30m \
  bash scripts/run_retrieval_bench.sh

# 4. 示例：单独测更大 TopK；筛选条件通过 FILTERS JSON 环境变量传入
MODES=both RATES=200 DURATION=15m TOP_K=50 \
  bash scripts/run_retrieval_bench.sh
```

输出目录默认在临时目录下，也可用 `RESULT_DIR` 指定一个不存在的新目录。每轮输出 JSON 指标、运行日志，以及整批 `runs.csv`；不会覆盖旧报告。k6 路径可通过 `K6_BIN` 指定。

默认要求有效响应比例不低于 99.9%、搜索 HTTP 失败比例不高于 0.1%、`dropped_iterations=0`，可通过 `MAX_ERROR_RATE` 调整。这只是**寻找容量的实验阈值，不是已经约定或达到的线上可用性 SLO**。长期验证应单独审查每一类错误，不能把 429 也当成功。延迟默认仅报告；若要增加临时保护线，可设 `P99_LIMIT_MS=1000`，这 1 秒是可调整的实验限制。

## 观察哪些指标，如何定位

| 指标／现象 | 数据来源 | 解释与下一步 |
| --- | --- | --- |
| 有效请求数、失败比例、搜索 P99 | `bench_valid`、`bench_http_ms` | 有效表示接口结构正确，不表示推荐相关性合格；准备模型向量的时间不混进搜索延迟 |
| 429、5xx、网络／超时失败 | `bench_limited`、`bench_server_error`、`bench_transport_error` | 分别排查测试并发上限、服务异常和调用路径；不能统一解释成 Qdrant 性能问题 |
| 发不出目标请求量 | `dropped_iterations`、发压机 CPU／网络 | 先排查发压机和 VU 数；服务变慢也会耗尽 VU，不能直接归因于客户端 |
| 进入线程池前等待增加 | `bench_dispatch_wait_ms` | 线程池或进程调度拥塞；与 CPU、存储耗时一起看 |
| 存储耗时增加 | `bench_store_ms`、向量／关键词子项 | 包含原有索引锁等待，不能直接称为 Qdrant 算法耗时；对照后台更新和 CPU |
| 结果大面积为空 | `bench_empty_results` 与人工核验 | 可能样本／筛选不匹配或索引未就绪，不能凭高速空结果证明容量 |
| CPU、RSS、重启、磁盘写入、剩余空间 | 服务端监控；必要时用 `pidstat -dur -p <PID> 1` | 记录容器配额与进程数量；info 的 RSS 是历史峰值，不是实时值 |
| 日志增长 | 各实际日志目录、平台采集指标 | 同时覆盖 Python、stdout、访问日志、平台采集；轮转、压缩、删除时目录大小差不等于写入字节数 |

当前测试并发上限默认 32；k6 默认预分配 32 个 VU、最多 128 个。需要的并发大致为 QPS × 请求耗时（秒），再留波动余量。例如 1,667 QPS、100ms 对应约 167 个在途请求。不要把默认上限导致的 429 或发压不足当成存储极限。本实验接口最多允许 128 个在途搜索；若达到该保护上限，需要先定位瓶颈，再决定是否改上限，不能据此断言更高吞吐不可实现。

存储接口绕过推荐阶段的候选明细日志。因此当前日志对照只能说明存储路径及公共 HTTP 日志开销；完整业务日志必须在端到端阶段再测。日志治理优先检查高频明细是否需要逐条输出、保留期和总量上限，再评估异步队列；异步化仍需验证队列满时的丢弃或阻塞行为。

## 上线前再补两组验证

**完整搜索容量：** 从实际搜索入口测试常见查询、长尾、复杂筛选、冷缓存和热缓存，分别记录模型、检索、排序及返回结果耗时。用真实查询分布评估缓存，不把本实验 64 条循环查询的命中率带入容量预算。Embedding、精排等模型服务按最终链路选择接入和压测，不要求所有请求调用所有模型。业务返回失败、空结果、降级结果分别统计。

**高可用与恢复：** 在稳定业务流量下验证模型超时／不可用时是否能降级、实例退出时是否摘流、剩余实例能否承载流量、恢复后是否抖动；验证启动加载、资料更新失败、缓存失效及过载限流。先单实例退出，再按既定部署拓扑验证可用区级故障。除请求成功率外，记录降级比例、恢复时间及结果正确性。短时间压测通过不能证明全年 99.99% 可用性。

## 如何得出选型与实例数

- Local 的稳定容量、资源占用、更新影响和恢复时间满足要求，且运维成本可接受，就保留；不要仅因名称是 Local 就立即迁移。
- 如果读写争用或每进程复制索引导致成本过高，先确认实际瓶颈，再做 Server 对照。对照应保留相同关键词语义和数据，不能把两种不同检索实现的 QPS 直接比较。
- 存储压测只能给出存储容量。用最终业务链路的稳定单实例容量乘以规划利用率，得到有余量的 `q`。规划利用率先以 70% 举例，最终结合抖动和故障结果确定，避免重复打折。
- 若采用三可用区均匀部署并要求容忍一个区退出，总实例数可先估为 `3 × ceil(1667 / (2 × q))`，随后必须验证剩余实例的集群吞吐、模型配额和流量分配。每分钟峰值还可能包含更高的秒级突发，需要补流量分布。
